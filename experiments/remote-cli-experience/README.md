# One-owner remote CLI experience (experimental)

**FAKE loopback provider; Docker Linux loopback only. No credentials, real SSH host provisioning, Mac, WAN or production code.** This reuses the existing native question RPC owner/policy and pinned SSH fixture instead of cloning either lab. The narrow owner adapter adds /experience/hello, /experience/launch (single in-memory owner with fixed-ID duplicate acceptance), and /experience/events (unprojected RPC event values). /answer is the existing native targeted-question path. This is not the task-poc owner: that owner has stronger append/fsync and paged cursor semantics, but its /lab/reply is a *modeled* question, not the native service. Joining them requires changing the owner; this adapter deliberately prioritizes a real native question within one CLI.

Build from this worktree with Bun 1.4.2 and installed dependencies:

    bun install --frozen-lockfile
    bun scripts/prepare-assets.ts
    bun scripts/build.ts --outfile=dist/die-remote-cli-experience

Or use `--reuse-web` with matching T3 source revision and patch asset provenance (see dist/die-web/SOURCE.txt); do not treat unrelated web assets as equivalent. Run:

    BUN_BIN=/path/to/bun DIE_BIN=dist/die-remote-cli-experience bash experiments/remote-cli-experience/run.sh
    BUN_BIN=/path/to/bun DIE_BIN=dist/die-remote-cli-experience bash experiments/remote-cli-experience/run.sh --interactive

The runner creates disposable SSH keys, checks wrong host-key rejection, pins the right host, stages die inside Docker, starts an owner on isolated Docker network (no HTTP port published), and forwards only through SSH. It saves intent and observed owner identity/epoch before the first POST; re-launch binds both and reuses the same ID only on that owner. A changed owner refuses replay. It cuts the client tunnel, checks cached offline transcript and failed live status, then reconnects, syncs, sends an **exact native question ID** and choice A, and checks bounded RPC event-prefix tool and final assistant values. In interactive mode type CLI commands at `remote-cli>` and `continue` to advance between stages. `offline` works disconnected; `status` requires SSH. Other commands: `connect`, `launch`, `sync`, `transcript`, `answer <id> A`. The runner automates advancement, so manual launch/answer repeats are deduplicated/rejected. To preserve local cached events after Docker shutdown set `LAB_EXPERIENCE_STATE=/tmp/remote-state.json` and inspect offline with `REMOTE_CLI_STATE=/tmp/remote-state.json bun experiments/remote-cli-experience/cli.ts transcript`. State is local mode 0600; keep it private. `bun test experiments/remote-cli-experience/cli.test.ts` checks rendered offline values, pending uncertain send, stable retry ID and owner mismatch.

Limits: owner /work is tmpfs, not crash durable; owner restart identity changes and client refuses merge/replay. Launch intent and owner identity/epoch are fsynced locally before sending, but owner acceptance is not crash-safe and restart cannot resume. RPC events are retained unprojected in the live owner (180-event bound; 65,536-byte line bound in experience mode); any overflow reports an error, **not a full transcript**. A successful sync copies the bounded event prefix to local disk and fsyncs before displaying a fresh state. There is no page/cursor protocol; every sync rereads the bounded prefix; no history across a dead owner and no guarantee of crash-safe owner disk. Remote accepted != provider success; native reply submission != delivery; sync verifies native ledger status. The fixture only permits choice A. Real config discovery, profile changes, cancellation, Mac capabilities, repo transfer/return and real provider auth are next steps, not implied by this run. CLI displays RPC event JSON, not a polished chat renderer. The bearer is a fixture gate, not security against same-UID agent code; don't use on a real host.

The offline view displays owner identity/epoch, event count/cap, last sync and any overflow/gap refusal. These are bounded event-prefix values, not full historical records. An answer saves sending/outcome-unknown before the POST, then submission; only a later ledger sync confirms delivery. An uncertain answer cannot be casually resent. The integrated endpoint validates exact native ledger owner/version plus fixture owner identity/epoch; the original unscoped probe /answer retains its legacy validation for the shared native probe. Fixture completion is narrowly evidenced by the owner seeing the explicit final "SAVED ANSWER OBSERVED" message and native delivered ledger, not by counting agent_end events.
