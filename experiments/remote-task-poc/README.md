# Durable remote task vertical lab (not production)

From repo root: `BUN_BIN=/absolute/path/to/bun DIE_BIN=/absolute/path/to/die bash experiments/remote-task-poc/run.sh` (omit overrides if binaries on PATH / dist/die available). Docker Linux required. No web build, provider account or credentials. The runner creates a unique image/container and randomized loopback host port; tears them down on success/failure. Root filesystem read-only, non-root container, unique disposable Docker /work volume (persists across container restart until cleanup); no home, repo or Docker socket mounts. Fixture and HTTP adapter share a container; the host Mac is represented by short-lived client processes, **not tested on macOS**.

Actual die RPC runs in Linux container, with explicit `--provider loopback --model loopback-model --thinking off`. Fake deterministic OpenAI-compatible SSE model drives real execute/shell/Bun.file tools and three model turns. Profile is an independent remote default, unrelated to Live. Handshake advertises protocol, owner identity/epoch, profile and **synthetic-only auth readiness**. A fresh per-run bearer token is required for every HTTP route, including the fixture model endpoint. This is a loopback test adapter, not remote network authentication/TLS or a paid-provider auth verification.

Accepted request and sequenced event records are append-only JSONL with fsync before response; one task maximum, 159 data events plus one reserved terminal event, 20kB/complete JSON event cap, 10 events/30kB summed event-JSON payload per page (response envelope extra), 65-second watchdog. Client appends/fsyncs each complete event locally. Question and capability records/replies also fsync before response; answer/capability replies have fixed IDs and conflicting retries reject. Different process reconnects after 4 seconds with no host requests; tool outputs and final assistant text are saved in full on client disk and read after container stop. Stable launch ID retries deduplicate; prompt/config conflicts, bad versions/profiles, wrong bearer and cursor mismatch reject. Owner restart keeps identity, increments epoch, retains completed outcome or marks in-flight task unknown; client refuses to merge across epochs. Runner restarts the completed owner against its Docker volume and checks epoch change and client rejection. It does not test interruption mid-task. This is not exactly-once external effects or power-loss-atomic transaction; abrupt kill can tear a JSON line, and no repair is implemented.

The second, fresh-owner fixture models a persisted question and an independent typed read-local-fixture capability. Real die execute tools do an independent marker read, request both lab dependencies, and (after a later RPC prompt) fetch their explicit results into a real tool transcript. RPC's parent-only /questions UI is not externally answerable through this harness: these /lab endpoints are **a modeled dependency transport, not harness questions or shipped approval plumbing**. The script explicitly submits a fixture answer; product code does not autoanswer. The local client reads only the explicitly configured LAB_FIXTURE_FILE temp file for the allowlisted capability, and sends bounded contents with fixed IDs; Docker cannot read it. Permission denial is a separate terminal run. No arbitrary path/shell capability or local CLI/skills/repo copy. A wait leaves RPC alive and is not a crash-safe continuation; unfinished owner restart remains unknown. Remote repo setup, real authentication/SSH, actual voice and provider remain **unimplemented**. No credential/repo/skill migration. A real deployment needs persisted pending questions and explicit replies before running such tasks. A cap persists a capped outcome and terminates the agent (RPC stdout line buffer capped at 256KiB); later restart is unknown, not replayed. Replica meta is a separate write (not transactional); a crash between appends and meta handling needs manual reconciliation. Reported event JSON UTF-8 bytes, replica file bytes (including newlines), and post-detach catchup bytes are separate; all omit HTTP/TCP overhead and Docker build bytes. Offline CLI prints the full bounded event transcript with its summary. The runner prints staged die version and SHA256 provenance.

Strict standalone types: with TypeScript, @types/bun and @types/node installed in repo node_modules, run `tsc -p experiments/remote-task-poc/tsconfig.json`. Run `bun test experiments/remote-task-poc/*.test.ts` for bounds and idempotency checks. Runner performs integration protocol assertions and transcript checks for independent work, offline pending question, explicit reply/capability, denial and completion. Runner removes temporary output unless LAB_TRANSCRIPT is set. To keep and read a transcript after the server is gone:

```sh
LAB_TRANSCRIPT=/tmp/die-offline.jsonl bash experiments/remote-task-poc/run.sh
bun experiments/remote-task-poc/client.ts offline /tmp/die-offline.jsonl
```

Offline mode makes no network request and labels the data as cached. The saved transcript and its .meta file remain until you remove them.
