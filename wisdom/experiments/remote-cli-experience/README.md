# Integrated remote CLI transcript experiment

Fake loopback model, real die RPC/native question service, disposable Docker owner reached through pinned SSH. No real credentials, Mac, WAN, production deployment or task resumption. This extends the existing single CLI path, not the task-poc modeled-question protocol. Read wisdom/remote-workspaces/user-decisions.md.

The owner persists each complete RPC JSON event before exposing it. Its append-only hash-chained journal assigns stable sequences and serves at most 16 events per page, each at most 65,536 bytes; the client requests from its fsynced journal sequence/hash cursor (state lag after a crash invalidates stale question/completion metadata and is reconciled; state ahead of the journal or a conflicting prefix refuses) and persists each event to its own fsynced journal before advancing local state. Each sync pins the first page high-water sequence and reports observed-through that boundary; later appended events require another sync. Question status is separately observed metadata, not proof that subsequent transcript events were copied. The owner may advance immediately after any response. Sync never fetches the entire previous prefix. Page payload memory is bounded, but the journal on each side grows without automatic pruning and its in-memory offset/hash index grows with record count; budget disk and index memory accordingly. Offline/transcript reads all locally persisted conversation and tool text after SSH and owner stop. Large files are not embedded in events; a bounded Git fixture bundle and result patch use a separate explicit transfer path described below. Invalid page sequences, changed cursor, truncated/corrupt journal, excessive RPC records and owner errors refuse a complete transcript claim rather than pretending a prefix is whole. The owner keeps a bounded recent 180-event memory window for fixture assertions; its /work journal is tmpfs in this run, so durability is across process observation, not container deletion or disk crash.

Run with Bun 1.4.2 and a built die executable:

    BUN_BIN=/path/to/bun DIE_BIN=/path/to/die bash wisdom/experiments/remote-cli-experience/run.sh
    bun test wisdom/experiments/remote-cli-experience/*.test.ts wisdom/experiments/remote-native-question-probe/*.test.ts wisdom/experiments/remote-task-poc/*.test.ts

The runner checks wrong SSH host-key rejection, offline reading after tunnel loss and owner stop, launch ID deduplication, exact native question owner/version and final answer delivery. Set LAB_EXPERIENCE_STATE=/tmp/remote-state.json to retain local state; copy both /tmp/remote-state.json and /tmp/remote-state.json.events to preserve offline text (private files). Do not replay a launch after owner identity/epoch changes: acceptance and an active task outcome are unknown on owner crash, and no owner task is resumed. No automatic retry elsewhere. The native question ledger still governs answer permission. This is a small experiment, not a general remote workspace, arbitrary file artifact transport, production-safe repository integration or production sync service.

## Disposable Git fixture return (experimental)

Run `BUN_BIN=/path/to/bun DIE_BIN=/path/to/die bash wisdom/experiments/remote-cli-experience/run.sh --repo-safe` or `--repo-conflict`. Both create their own disposable repository; do not point automated tests at a user repository. The same CLI also accepts `launch-repo <repo-root> --allow-history-bundle [--include <exact-untracked-path> ...]`, followed by the existing `launch` retry, `sync` / `answer` and, only after confirmed fixture completion, `return`. Explicit `--include` is the only grant for an untracked file; no question response is interpreted as transfer permission. This command is for disposable fixtures only: the Git bundle transfers reachable history (which may contain secrets) as well as the selected tracked snapshot, even though omitted untracked files are excluded. The required `--allow-history-bundle` flag is an explicit acknowledgement of this Git-history transfer, not a secret scan. The upload is capped at 6 MB, patch at 4 MB. No production remote command is exposed.

The owner clones the bundled immutable snapshot into the die process working directory before launch; the fake provider makes and commits an edit with the real die shell tool, then follows the existing native question path. After the owner reports completion through durable sync, `return` fetches a task-ID/snapshot-bound result, verifies its SHA-256, saves a local patch artifact under the per-launch state folder, then calls the conservative handoff adapter. Safe regular tracked edits (including remote staged/unstaged tracked edits) apply to the working tree without changing the local index; other outcomes print a review reason and artifact path. Remote untracked files are detected, omitted from the patch and force review; this fixture has no path for fetching those file bytes after owner deletion. A second return refuses blind integration through the receipt. Keep the local state JSON, event journal and `.repo-<launch-id>` folder together. Owner /work and its cloned repo are tmpfs: deletion loses results; a new owner epoch is not resumable. No cross-process lock, general repo security audit, remote persistence, crash-atomic integration or production transfer service is claimed.

## On-demand repo-file read fixture

Run 
`BUN_BIN=... DIE_BIN=... bash wisdom/experiments/remote-cli-experience/run.sh --repo-read` (also `--repo-read-denied`, `--repo-read-cancel`). These are disposable Docker/SSH, staged die, fake-loopback-provider runs, not Mac/provider proof.

`launch-repo <root> --allow-history-bundle --grant-repo-read` makes a single explicit current-repo-root grant for this task. `sync` shows the pending owner/task/request; `serve-read` reads the exact requested relative path (this first fixture only requests `on-demand.txt`) and replies through the pinned owner and task. No per-read prompt. `cancel-file-task` terminates this fixture task. Without the client the real remote die execute completes an independent step and then waits for the local file reply; reconnect, sync and serve-read resume it. UTF-8 only, 16 KiB regular file, canonical path confined to the granted root; symlink escape, absolute/parent paths, missing/oversized/invalid UTF-8 are denied and visible to the remote execute, not silently substituted. The untracked fixture file is deliberately omitted from the Git snapshot and is not pre-copied to Docker.

Pending/resolved/cancelled events join the owner's hash-chained event journal and the current owner saves pending metadata in /work; the client persists reply intent before posting. Same response retries are idempotent, conflicts and late terminal replies reject. There is no owner restart recovery (owner /work is tmpfs), general path-request language, general RPC capability bridge, whole-machine authorization, credential transfer, file mutation, or shell sandbox. Existing repo snapshot Git-history sensitivity and return limits still apply. Remote die itself has ordinary tools in its disposable checkout; the grant only governs this narrow local file-read bridge. Do not use the fixture for an arbitrary user repo.
