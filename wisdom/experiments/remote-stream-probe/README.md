# Loopback stream probe (experiment only)

From repository root: `./experiments/remote-stream-probe/run.sh`. Tested with Node 24.21.0 (built-in TypeScript stripping); set NODE_BIN to select it and repository dev dependencies for strict `tsc`; no Docker, credentials, socket/home mounts, LLM, or external services. The runner checks strict TS, runs unit tests, runs 19 scenarios, writes `results.json`, and asserts all expected events arrived. HTTP servers bind random 127.0.0.1 ports, close in `finally`; each scenario has a 6s request deadline and finite event count. No Compose project or fixed-port network-lab resource is touched.

**Candidates:** one shared 25ms polling loop; compact shared long-poll highwater/gap hints plus cursor-paginated fetch; and direct data-bearing shared long-poll returning bounded pages. Each uses a handshake epoch and client cursor. No client reads server state for flow control. A single outstanding request avoids per-task poll loops; short-lived responses avoid stream socket backpressure in this probe. Hint queue max 4096 bytes, measured as the sum of serialized `{cursor,epoch}` entries, **excluding** response-envelope and framing overhead; overflow sends explicit `gap` and client catches up. A highwater hint contains no event payload. The direct candidate does not use this queue. Queue is in-process application state, **not** measured HTTP/TCP send-buffer bytes: this does not prove slow TCP-reader safety. Pages cap at 64 events and 32 KiB for the complete JSON response (including envelope). An individual record too large for either retention or a page is rejected before advancing the cursor. Authoritative retention separately caps serialized events at 2 MiB; older cursors and epoch changes return `history unavailable` (cannot promise transcript recovery). Cursor replay dedupes, checks contiguous order, and detects conflicting recent duplicates. Real deployment needs durable retained log, identity/auth, reconnect and socket backpressure tests.

Server-created monotonic timestamps and client visibility run in one Node process. Loopback impairment sleeps per direction **at HTTP application level**, not Toxiproxy or WAN, no bandwidth cap. 100/300ms each way represents minimum ~200/600ms request RTT. Prior Toxiproxy bandwidth toxic uses **KiB/s**, not bytes/s; no bandwidth toxic is used here. Client visibility is after JSON parse and contiguous replica apply. Acceptance/progress/question/result are synthetic timed at 10/100/220/460ms (burst question at 120ms). No real LLM. 100/1000 streams are objects, not processes; baseline is **one shared 25ms polling loop**, so its request counts do not represent per-task polling. Urgent acceptance/question/result bypass candidate 0/10/40ms progress batch delay. Frames count JSON HTTP responses, **not packets**. Application bytes are JSON response bodies plus URL paths for requests (GET no body), not HTTP headers, TLS, SSH, TCP bytes, or compression. No codec conclusion.

`results.json` holds raw compact summaries including n/min/median/max per event kind; n=1 per timing category for the single task normal runs, so don't infer tails or p95. Timers and event-loop scheduling cause run-to-run variation. Burst 1-task run creates 12 extra progress events; the reconnect run pauses the reader 550ms, creates 128 x 4096-character transcript chunks (~512 KiB), overflows the notification queue, then recovers all 132 events in bounded pages. This models absence of client requests, not a genuine severed TCP connection. Unit tests force retention exhaustion, oversized add, byte/count page boundaries, and epoch mismatch; missing history is explicit and not silently fabricated. History is only in memory; restart changes epoch.
