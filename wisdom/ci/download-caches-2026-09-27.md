Cache inventory:

- Bun 1.4.2 downloads in $RUNNER_TEMP/die-bun-cache via `BUN_INSTALL_CACHE_DIR`; key includes OS, architecture, Bun version, `bun.lock` and root `package.json`. Restored before `bun install --frozen-lockfile`; job completion saves newly populated cache. The macOS CI lane also installs root dependencies, so it gets its own OS-scoped cache.
- T3 pnpm v11 store in $RUNNER_TEMP/die-pnpm-store via `PNPM_CONFIG_STORE_DIR`; key includes OS, architecture, **resolved upstream pnpm 11.10.0**, pinned upstream source JSON (thus upstream lockfile revision), and `die.patch`. The setup action bootstraps pnpm 11.27.1, but the pinned upstream packageManager is 11.10.0; using the bootstrap version as the cache key would be misleading. The pnpm store puts its content in the `v11` subdirectory. Locally `pnpm store path` changed from default `~/.local/share/pnpm/store/v11` to `/tmp/die-cache-probe/v11` using this variable; lowercase `npm_config_store_dir` did **not** work with pnpm 11.27.1.
- No restore prefixes, no node_modules, compiled outputs, web archive, source checkout, HOME, tokens, or user data. A checkout cache is tempting but buildWeb must check the pinned SHA, apply patch and verify source each time; caching checkout/patch state risks stale or untracked data. TypeScript has no enabled incremental build; web Vite/backend bundling and Bun compile lack an observed safe isolated cache worth the complexity. Existing exact-SHA release-artifact reuse remains the only compiled-artifact reuse; this change never uses a partial-key dist cache. Build still executes source verification and artifact checks.

The hash inputs force different pnpm keys when source pin or patch changes, including patch dependency changes. Bun keys rotate when the root manifest/lock changes. Jobs retain their frozen installs and the normal full build, tests, smoke and portable native-dependency verification on hits. Cache entries are immutable; a first run with an exact key can leave later package additions to be downloaded again until key rotation, not invalidate correctness. GitHub cache branch visibility can constrain tag/PR hits; **hosted hit rate and wall-time benefit are unverified** until these workflows run. Other potential caching (a separately verified pinned source Git object checkout or compiler incremental metadata with full source/tool/platform identity) needs measured benefit and a non-bypassable verifier; not warranted yet. Never place credentials in any future cache.
