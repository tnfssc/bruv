## Answer

**Native Claude's richer handling is predominantly host-side protocol projection, not a property of the Claude model backend.** At the inspected pin, ClaudeAdapterV2 consumes SDK envelopes, task lifecycles, causal tool IDs and control semantics, then emits ordinary T3 V2 nodes, child-thread projections and turn items. A different engine faithfully implementing that contract can potentially reuse these projections in **unmodified native Claude T3**. It does not need Claude to generate an answer just to get this UI. But neither changing tool names nor emitting arbitrary Claude-looking task outcomes constitutes that implementation. Host selection/model catalog, SDK startup/auth/options/storage and real engine controls remain separate gates.

Two distinct desired outcomes:

1. **Bruv-owned workers:** real existing Bruv jobs, projected as provider-native subagents. Bruv remains execution/cancellation/delivery authority. T3 can allocate a *projection* child thread for their real conversation; this is not a second runnable child agent and not a T3 scheduler takeover.
2. **T3-owned delegation:** a real invocation of the supplied T3 MCP `delegate_task`, committing an app-owned child thread/run. T3 owns execution and completion acknowledgement. Bruv must not also launch a local worker for it or emit a duplicate provider-native task.

This is not the generic claude-acp registry path: generic ACP is handled by a different adapter and lacks these native Claude branches. Prior ACP cancellation/steering findings cannot be assumed to describe native Claude.

## IDs: do not conflate them

Let J be an actual Bruv job ID, P the root T3 provider-thread ID and T the translated native task ID. Connector must persist an injective **J ↔ T ↔ launch-call ID ↔ actual child session** mapping under the real parent session. Local task IDs, session-file paths, SSH `ssh:<encoded taskId>` and native T3 node IDs are different namespaces. A namespaced T is permissible protocol translation; a fabricated runnable child is not. CA's node IDs omit provider-instance/session scope except whatever is already embedded in T, so choose globally unique stable task IDs, not a resetting small counter.

Exact CA derivations (allocator `joinId(prefix,...parts)` percent-encodes **each part once**):

- Subagent/node ID: `joinId("node","provider","claudeAgent","native-item", "task:"+T)`.
- Child root node: same derivation with native item `task:T:thread-root`.
- Projected child thread: `joinId("thread","provider","claudeAgent","native-thread", P+":"+T)`. This **does not expose a native child session ID**.
- Parent subagent turn item: `joinId("turn-item","provider","claudeAgent","native-item", "task:"+T+":subagent")`.
- `nativeTaskRef = {driver:"claudeAgent", nativeId:T, strength:"strong"}`; subagent's providerThreadId and child's activeProviderThreadId are null. Projected child thread's creationSource is `provider`; subagent origin is `provider_native`.
- `session_id` is the root CLI-native session identity. `uuid` is a message identity. `tool_use_id` links task start/progress/terminal to launch (or resume) call. `parent_tool_use_id` attributes child assistant/user/stream frames to the child whose launching call owns them; it is **not** task ID or session ID.
- Bruv AgentInfo already records actual `sessionFile`, `parentSessionFile`, type/model/thinking/depth, phase and currentTool. TaskManager `onTaskChild` links J to child session before launch event publication. Existing web telemetry **drops** that mapping.
- Monitor has no separate native monitor UUID/thread: T is its background task ID, associated with a real `Monitor` tool-use ID and native root session. It becomes a pending roster entry `{taskId:T,kind:"monitor",description}`, not a subagent child thread.

There is no generic SDK `task_replay` or `task_cancelled` frame in this contract. SDK user replay is `type:"user", isReplay:true` with actual original message/session/parent identity; job replay is reconstruction from real lifecycle/roster plus T3 persisted state, not a second launch. Never blindly replay an old task_started after its terminal projection: CA treats authoritative starts as reopen events, not harmless snapshots.

Reopening a real task is allowed only by authoritative `task_started` (e.g. real child resume). Late `task_progress` must not resurrect completed work. On resume the task keeps node/child identities, can acquire current runId and new runToolUseId, clears stale final/progress, and appends the new prompt. Do not emit another start merely because a socket reattached.

## Exact emitted T3 event families

CA 4133–4315 emits `app_thread.created` once for a new real provider-native child; `node.updated` for the parent subagent node and child root when lifecycle changes; `subagent.updated` and `turn_item.updated` (type=subagent) on state/progress updates. Child prompt/assistant/result artifacts emit `message.updated` and `turn_item.updated`; repeated final summary matching the actual child assistant text is deduplicated. Both child/subagent nodes have countsForRun=false: T3 UI subagent summary counts observed runtime subagent statuses, not fabricated root-turn completion counts ([agentSpawnSummary.ts](https://github.com/pingdotgg/t3code/blob/fed41fa88bb27cb4325cb208d571393850bc63c2/apps/web/src/components/chat/agentSpawnSummary.ts)).

Opaque commands/monitors update `provider_thread.updated` with pendingBackgroundTasks (CA 3398–3420), rather than emitting child/subagent nodes. Actual wake detection calls `continuationRequests.offer({threadId,providerThreadId,driver,detail,notification?})` at CA 5224; it is not an arbitrary SDK “task finished means assistant answer” event. Root started/completed provider-turn and turn-item events must describe the real root execution.

## Steering, child control and settlement

**Active Steer**: CA 7266–7301 requires a live query and matching active providerTurnId; offers an SDK user message with `priority:"now"`. It **does not first interrupt or close** the query. CA remembers steering and ignores interim result `terminal_reason:"aborted_streaming"|"aborted_tools"` from that steering abort, awaiting the corrected turn's final result. A compatible Bruv endpoint must apply actual Pi/Bruv steer semantics while tools/loop are active, not simply acknowledge priority or implement abort+restart and call it parity. Native-Pi steering findings establish that the engine has an appropriate active-input operation, not that Claude-compatible translation already routes it. Steer may abort the current model stream/tools as part of the engine’s priority-now semantics; the claim is **not** that every active foreground tool always survives. It is distinct active input rather than host interrupt/close/restart. Ordinary sends and follow-ups are not automatically Steer; priority, active run matching, prompt UUID echo and result ownership must be preserved.

**Root Stop**: CA 7178 onward calls query.interrupt **and query.close**, waiting for stream closure, not just marking a tool cancelled. With no active foreground but `requestRuntimeRestart`=true, it closes the live query, clears wake state and invalidates old process roster. Source assumes CLI-owned shells die with that CLI. Bruv jobs that survive foreground abort/connector exit would violate that assumption unless native-root Stop explicitly controls those owned jobs or the accepted semantics are changed. Never report task stopped before actual backend/process confirmation. Protocol-compatible cancel acknowledgement does not establish stopped execution.

**Individual native child control is limited**: SDK exposes stopTask(T), but CA's query abstraction/returned adapter does not expose it; native subagents advertise canCloseSubagents=false, canWaitForSubagents=false and no native child-thread IDs/fork. T3-created provider child shells are not automatically sendable live Bruv sessions. Model/native-tool `TaskStop` or `SendMessage` is a separate engine operation and must target actual jobs/sessions. No claim that displaying a child grants UI steering/cancel/fork of that child. For Bruv's own `jobs.stop(J)` keep Bruv authority; app-owned MCP task_cancel applies to real delegated tasks only.

**After settle**: CA preserves live process for background work, refuses model/policy replacement that would destroy it (CA 6789–6925; test 7229), and handles idle lifecycle separately. Known background task completion plus genuine wake turn init/output can request one provider continuation. Nested completion is buffered for child projection but must not wake root. Unknown notifications do not schedule a spurious turn. Prompt echo/UUID gating separates earlier CLI wake output from the next user's offered prompt; task-notification-origin results are handled specially. A compatible binary must keep late child notifications flowing after result, not exit after the answer or copy all child text into the next user turn. It must also avoid competing automatic Bruv/T3 root continuations: T3 owns the continuation run while Bruv remains the executor/message source. Existing lifecycle prototype's hold-open/interrupt-restart proof is **not** proof of this native Claude wake path.

Resume lookup is an additional **storage** contract: getSubagentMessages is an SDK file reader, not a stdout request to the replacement binary. Mapping task_id to a Pi session file does not make it succeed. Need faithful public-compatible session artifacts or an explicitly bounded no-resume limitation. Do not invent child sessions/outcomes to satisfy that lookup.

## T3-owned MCP split

Official delegate_task accepts task, optional target/title/role, mode async/wait, clientRequestId and runtime/interaction mode. It inherits workspace; independent worktree flow is separate. Result returns real taskId (NodeId), childThreadId, nullable childRunId, childNodeId, provider/model, status/workState, pending-child state, terminal summary/context-transfer identities and waitTimedOut. A wait timeout does not cancel the child. At CA 935 onward, the native adapter supplies real T3 MCP query configuration; the compatible engine must consume/call it, not just advertise the name.

OrchestratorMcpService readTask filters **origin app_owned**. Terminal task_status acknowledges committed completion delivery; task_cancel requests actual app-owned child cancellation/disposes delivery. This is independent from provider-native task_notification. A Bruv orchestrator profile only grants delegation permission; it does not become T3 V2 scheduler by name. Existing Bruv `T3NativeTaskAdapter` expects patched `bruv_task_launch`, `bruv_task_observe`, `bruv_task_cancel`, `bruv_task_list` tools (version=1 result/profile/depth contract), **not** the official delegate_task schema. User's potential orchestrator-only routing requires explicit profile→catalog target/policy/depth mapping through the supplied official MCP and no duplicate local launch. It is not already supported merely because the bundle has native delegation.

## What the current source of truth covers

- TaskManager owns local spawn/process state/output/confirmed close and emits typed `spawned,updated,activity,stopping,completed` snapshots (76–81). AgentProgress decodes public child JSON events and maintains phase/currentTool/actual bounded answer; onTaskChild supplies actual session linkage (303/335, 691 onward). JobService is the unified facade over local manager, native backend and SSH owner, **not one uniform lifecycle stream**.
- Existing `bruv_task_event` is merely RPC-mode opt-in presentation: `started/completed` only, shortened command and profile metadata; no progress/child-session/causal tool IDs/results/replay/stop request. Unmodified official native Claude does not consume that Bruv event type. It is evidence of real lifecycle authority, not a ready Claude wire contract.
- MergedTaskMonitorSource is explicitly a read projection. Its monitorIdentity for SSH is host/job-owner/epoch identity, not a Claude monitor ID. Preserve existing ownership rather than building another executor/task registry in the connector.

## Small acceptance slice (before implementation promise)

Use unchanged official native-Claude T3 with the compatibility binary, isolated settings/home, no paid credentials. A fixture may prove parsing/control only; mark it separately from real local execution.

1. Two **real Bruv normal workers**, stable J/T/launch/session mapping recorded; simultaneous UI running count=2, phase/progress from real state, distinct child text/tools. One succeeds with actual bounded answer, one really fails; no Agent-tool-name-only fake completion.
2. One real background command and, only if implemented, one genuine watcher. Check command/monitor roster, real output, exact stop-request→confirmed terminal ordering. Do not confuse Bruv task overview with watcher execution.
3. While real foreground/tool work is active, press rendered **Steer**. Capture priority now and actual engine steering; correction reaches same active execution without root interrupt+close. Press **Stop** separately; prove intended root/owned-child scope and no orphan or automatic unowned answer after stop.
4. Let a worker finish **after root result**. Prove its exact terminal state, one T3-owned continuation, real late answer, no loss/duplication/misattribution to a later user prompt; nested completion does not wake root. Check reconnect/reload stable IDs and terminal monotonicity. Explicitly limit unsupported full process-restart/child-resume behavior until storage proof exists.
5. One explicit real MCP delegate_task via supplied T3 server; record returned committed child IDs and app_owned origin. No corresponding local worker/native clone. Verify task_status acknowledgement and separate task_cancel scope.

A native projection browser fixture can show richer UI independent of Claude backend, but only steps with real Bruv jobs/steering prove faithful compatible execution. If unchanged T3 cannot expose an intended child control, report that exact gap rather than spoof a controllable thread.

Values unchanged: existing one-owner, honest observed-state, durable identity and rendered-control acceptance rules directly cover this investigation; no new general principle was needed.
