## Decisive gates first

1. **A server executable cannot itself capture the browser user's microphone or play speech there.** Native Claude stream-json is not an audio device transport. T3 device panels mention microphone permissions for target devices, and browser screen recording exists; neither proves Bruv Live PCM/playback/AEC/session integration. No such native-Claude bridge was found. Local T3 terminal could run Bruv's local helper; remote server terminal opens server devices, not the user's Mac/browser. A local companion attached to the same backend needs a supported one-owner control path and real device proof. If remote browser-local Live is required, this remains a hard missing surface: additional client audio companion, upstream facility, or explicit human acceptance of narrower workflow. Dictation/uploaded audio/server mic is not equivalent. Do not mark voice out of scope.
2. **Native Claude presentation/maintenance isn't generic.** Official Claude driver has fixed Claude presentation, bundled Claude model catalog/capabilities and Anthropic package maintenance. Custom model strings don't establish arbitrary provider discovery, all thinking levels, honest usage/auth or safe updates. Bruv must identify itself honestly, never fake Claude/engine version or Anthropic subscription. Native update must not install/update the wrong product. Use distinctly named instance/terminal workflows where supported; exact misleading widgets remain a gap needing resolution before parity claim.
3. **Slash discovery isn't panel implementation.** Current nightly really offers provider commands and sends selected commands as leading prompt text. This can carry deterministic Bruv commands, not automatically host Pi custom panels, persistent inboxes, provider login/profile pickers or root pairing. Native structured questions or a same-owner terminal control client can provide equivalent human workflows. Starting a second writer with bruv -r against the active journal is NOT a workaround.
4. **Permissions aren't saved questions.** Claude capabilities say pending requests don't survive restart and approval callbacks are live-only. A live AskUserQuestion dialog cannot replace Bruv ledger/owner/version, saved/delivered/used states or explicit restart resume. Recover existing questions from their owner, not mint new answers. Permission denial isn't a question answer/cancellation.
5. **Idle completion/cancellation decide feasibility.** Launch receipt isn't finished worker; root Stop isn't necessarily descendants stopped. Need truthful workers/monitors, safe-boundary steering, distinct queues, idle wake, replay and one completion owner. Consume transport/fixture/task evidence below; Claude must be measured separately from failed generic ACP continuation assumptions.
6. **Runtime policy must mean what UI says.** execute runs arbitrary JS/shell/network/files. Calling it Read or adding model instructions doesn't enforce T3 read-only/plan policy. Enforce negotiated policy at executor/delegation, or reject unsupported restrictive operation honestly; never fallback to stronger tool. Blanket execute approval isn't per-file/per-command consent. Project trust, SSH/source approvals, billing and devices remain separate.
7. **Native fork/history is outside the executable wire.** SDK 0.3.276 forkSession and getSubagentMessages operate directly on Claude-layout filesystem journals; T3 does not pass a custom sessionStore. Implement a connector-owned faithful projection/cursor mapping without changing canonical Bruv originals, or provide an explicitly selected same-owner equivalent fork/history workflow. Emitting --fork or stdout frames alone cannot make the native button work. Wrong fork/context or corrupting old journals is a blocker.
8. **Platform/startup parity is a product choice.** Current Bruv runs Linux x64/arm64, macOS ARM and Termux ARM, with a bundled web app and no separate runtime install. Official external T3 may not ship every platform and requires its own installation. Preserve CLI, state and old executable; report exact unsupported platform/startup/offline changes before unbundling, not as accidental exclusions.

Parent can choose reversible terminal/control-client panels without routine questions. Real absent user-client audio, unavoidable misleading identity or unsatisfied safety/lifecycle requires explicit product resolution. None is waived by passing one prompt.
