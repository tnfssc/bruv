## What changed

[src/claude-compat/task-projection.ts](../../src/claude-compat/task-projection.ts) projects explicitly linked real Bruv jobs into native SDK task envelopes. It does not launch, inspect, cancel, subscribe, wake the root, own sessions, or make T3 child threads. Official ClaudeAdapterV2 makes its read-only provider-native child projections from these envelopes. T3 app-owned MCP tasks are excluded from every projection path.

Small public seams:

- projectTask(link, observation, previous?): pure normalized-source transition → frames and one tiny checkpoint.
- projectLocalTask(link, TaskSummary-shaped snapshot, context, previous?): real local snapshot conversion, including preparation and confirmed-close semantics. TaskEvent.task can go here; completed events need completion inspection if a result is available.
- projectChildFrame(link, {sourceSessionId,eventId,body}): route an already translated public assistant/user/stream frame from the actual linked child session. No log-to-conversation reconstruction.
- projectBackgroundRoster(root, snapshotId, entries): full opaque command/monitor REPLACE roster from the complete linked checkpoint snapshot. Workers are projected as subagents, not duplicate command roster entries.
- createTaskProjector({publish}): tiny awaited handler wrapper over those functions. publish receives the whole batch, including the next checkpoint. There is no internal map, bus, executor, timer, or task ledger.

## Identity and source ownership

Caller supplies the actual root native session_id, persisted Bruv root session identity, stable executor namespace, actual source authority, actual job ID, original real launch-tool-use ID, actual parent session and causal parent launch, plus the worker's real child session/parent link. Do not build links by reading tool names, prompt text, or launch timing. Keep job/session/source identities stable across reload. For an authoritative resume, set runToolUseId to the actual resume call while retaining launchToolUseId as the original child-frame owner.

Native task ID is bruv: + a deterministic UUIDv8 hash over task domain / namespace / Bruv root / native root / source / actual job. UUIDs are domain-separated deterministic hashes of task ID, actual persisted source event identity, and frame kind. Roster UUID includes the actual root identity and snapshot identity. No resetting counter, time-of-day identity, basename shortcut, or invented runnable child. As with UUIDs generally, uniqueness is cryptographic, not a mathematical injectivity claim.

The original launch/parent/child binding is checked against the checkpoint. Original launch and current resume calls must not be conflated. Source event IDs and monotone revisions come from the existing persisted link/source owner; TaskManager events themselves have neither. Stamp/persist them there, not in an extra task registry. Revisions must stay monotone per job across execution, resume and reconnect, and represent source ordering, not guessed timestamps.

T3 derives its own IDs with joinId percent-encoding each part once: node(provider,claudeAgent,native-item,task:T), child root with task:T:thread-root, child thread with native-thread P:T, and subagent turn item with task:T:subagent. This module emits T, not a synthetic native child-thread ID. The adapter's child thread is a projection of the actual worker session, not another engine execution.

## Engine/wire integration requirements

1. Persist the explicit job↔native task↔original launch↔actual child-session mapping with the existing session/job owner. Feed its real TaskManager/JobService source, not web bruv_task_event (that event drops causal and result data). Local helper verifies snapshot job/kind and AgentInfo.sessionFile/parentSessionFile. Preparation reservations do not count as a started child.
2. Serialize each root's input/delivery. publish must durably commit the returned checkpoint with the existing link and stage/deliver its frames through the session owner's existing ordered outbox. Do not send a batch, discard its checkpoint, then blindly replay task_started on reconnect. Partial delivery/retry and child-frame deduplication are the owner's responsibility; frame UUIDs are stable but do not make all adapter side effects idempotent.
3. Send the **real launch tool-use snapshot** through the wire translator before task_started. A worker's actual launch operation must be represented as Agent/Task for the adapter's launch metadata path; a real watcher must be represented as Monitor with its actual call ID. Do not fabricate a tool call for an arbitrary job. For a nested launch, route the actual launching assistant snapshot through the owning child's projectChildFrame first. Its parent_tool_use_id is the owner's original launch; nested task_started.tool_use_id is the nested launch. The adapter derives the nested owner from that call, not from a parent field appended to task_started. Keep source tool-use IDs globally unique through the wire translator's existing ID mapping, including all references.
4. Supply measured usage with progress. Local AgentProgress.phase/currentTool have useful real descriptions but **no token/tool/duration counters**. When counters are unavailable, omit task_progress; do not invent zero usage just to populate the SDK. The wire/session owner can supply actual model usage and source-observed counts/duration later.
5. Local terminal status requires completedAt, meaning the manager has confirmed closure. running + termination.requestedAt stays nonterminal. Canonical completed/failed/killed becomes SDK completed/failed/stopped only on actual terminal authority, never on stop request. Generic sources must supply explicit terminal.confirmed. Remote unknown stays unknown; a prior observed active checkpoint retains its last observed roster membership until confirmed exit, rather than claiming a new start/success. Map remote/native source statuses deliberately in their owner; the local helper is not a universal JobService adapter.
6. Inspect terminal output before projection when available. Pass the actual result summary and original artifact path, and mark source-observed truncation. If output has already been evicted, confirmed local exit still terminalizes with an empty summary, not a made-up answer. SDK output_file is a required string; absent artifact is represented as the empty string. No invented file path, automatic Pi-session-file substitution, or claim that it supplies replay. SDK wire/browser acceptance of the empty sentinel still needs the parent acceptance run.
7. Publish a complete root-session roster after every real background membership/terminal change, after committing corresponding cursors. It contains only observed active background opaque tasks; foreground tasks, terminal tasks, provider-native workers and app-owned tasks are omitted. Genuine monitor classification also needs its real launch tool-use frame upstream. Never feed a filtered page as a REPLACE roster. Unknown observations do not erase the last authoritative membership. No synthetic liveness probe here.
8. Continue accepting real linked child frames and confirmed exits after root result. Do not bind late output to a later user's prompt or start another root execution in this projector. T3/session owner owns continuation eligibility/drain. Nested worker completion ownership relies on the real nested launch snapshot. Full public child message bodies/tool IDs are supplied by the wire translator; AgentProgress stdout summaries are insufficient. A late actual child frame is routable after terminal; it does not reopen task lifecycle.

## Transitions and honest limits

Late/stale revisions are ignored. Once terminal, later starts/progress/snapshots cannot reopen; only an explicit authoritative resumed edge with observed running status can. Resume keeps the stable task and original launch/child identities, updates the current run call, and emits the authoritative start. A changed run call on a plain snapshot is rejected as stale. Initial unknown/preparing/unregistered-terminal observations produce no fake live child; historical launch and terminal reconstruction must come from actual persisted lifecycle authority.

No shell task_progress, invented monitor execution, duplicate app-owned projection, task_cancelled/task_replay custom frame, root result/wake synthesis, or stdout-based SDK replay. getSubagentMessages is a separate SDK storage-reader compatibility seam, owned elsewhere.

The pinned adapter **does not consume task_updated**. It learns backgrounded worker wake eligibility at task_started. Moving a worker from foreground to background later must not be papered over with another task_started: that is an authoritative reopen in the adapter. Shell promotion is correctly reflected by the full roster. Later worker background promotion/wake acceptance remains an adapter/session integration limit; preserve actual flags and prove supported async-worker registration in the parent acceptance slice. Also prove nested/background shell wake behavior before claiming root-vs-child continuation scope beyond the verified nested-worker launch path.

No persisted source subscription, session store, cancellation control, real worker/model invocation, native browser UI, process-restart recovery, or full child resume is claimed by this module alone. Those belong to the engine/wire/storage workers and the unchanged-T3 acceptance run.
