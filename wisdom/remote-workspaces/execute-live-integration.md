# Remote access through execute (Live-safe)

The normal root agent uses `remote.status()`, `remote.launch({repoPath, prompt, taskId?})`, `remote.sync(taskId)` and `remote.transcript(taskId, offset?)` from execute’s typed bridge. Remote operations live in `src/remote/operations.ts`; the root extension creates its own RemoteClient pointing to the same durable OS-user state as the `/remote` human command. Do not use a direct Pi remote tool: Main Live requires the ordinary execute-only loadout. Only the human `/remote connect` chooses the SSH host; agent calls cannot select or change it. For uncertain launch retry use the same task ID. Transcripts/status can be offline caches, not necessarily current remote state.

Evidence (2026-09-27): parent baseline `/tmp/die-remote-full-regression.log` showed 1232 pass, 18 skip, 2 Live TUI failures with direct remote tool. Docker-targeted Live TUI and remote unit tests after the fix: 17 pass, 0 fail (`/tmp/remote-target-tests.log`). Docker typecheck passed (`/tmp/remote-typecheck.log`). Built CLI + Docker SSH/fake-provider E2E passed, including agent execute launch, disconnected owner completion, reconnect sync and offline transcript (`/tmp/remote-e2e-run.log`, 64 events). No production SSH host was used. Values unchanged: existing human authorization and honest cached-status principles still apply.
