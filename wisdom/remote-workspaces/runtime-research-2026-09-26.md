# Whole-agent SSH runtime research — 2026-09-26

## Decision and evidence standard

The clarified requirement is **the entire agent on an SSH Linux server, continuing after the laptop loses network**, with remote custom CLI programs, skills and secrets. This supersedes the unresolved disconnect question in [ssh-research](ssh-research.md); [offline-first direction](offline-first-direction.md) records the same goal. Per [values](../values.md), place ownership where work must survive, distinguish acceptance/completion/delivery, reconcile unknown operations by stable identity, and prefer the smallest honest design. This is research, not implementation.

## What die currently does and does not

- Production `src/cli.ts` initializes the local Pi CLI, materializes runtime assets under the executing user's `~/.die/runtime/<version>`, then calls Pi `main`. It has no SSH target/remote attach command, remote bootstrap or remote version negotiation. `src/system-prompt.ts` reads the local runtime's `DIE_CODING_AGENT_DIR` or `~/.die/agent`; Pi's extension/skill discovery and project context are therefore a **runtime-host** concern, not solved by remote shell. The same applies to cwd, Bun and node filesystem/import resolution, subprocesses and custom executable PATH.
- `src/agent/extension.ts` creates `SessionHost` against its current Pi session manager and closes main owner and session host on `session_shutdown` (lines 486–511, 745–751). Its RPC-mode special case keeps print/JSON job service until jobs finish (around 585–594), not an SSH-hosted, laptop-independent agent. `src/history/session-manager.ts` is disk-backed; `src/tasks/job-service.ts` places launches at `ctx.cwd` and has a session-file launch ledger for T3, but neither turns local model/session ownership into a remote daemon. Questions, history, job delivery and subagents must all be owned and recoverable on the server, not merely shell execution.
- Die's model auth is not the SSH credential: e.g. `src/live/credentials.ts` shares runtime AuthStorage and locates `auth.json` under `DIE_CODING_AGENT_DIR` or `~/.die/agent`. Remote host needs independent usable provider credentials and network access. No automatic cross-OS skill/secret/CLI migration or consent model was found. Local keychain tokens, environment secrets and Mac executable files cannot be assumed usable on Linux.
- `experiments/remote-workspaces` has two bounded **same-machine Unix-socket simulations**: A has a persistent runtime/controller and keeps making agent decisions after viewer detach; B has a client controller and only a remote job continues while the controller is disconnected. `rpc-agent-demo.ts` additionally drives the real Pi RPC agent with a deterministic loopback fake model and a separate viewer that exits; its controller connection **does not** exit. [Prototype notes](ssh-prototype.md) and [README](../../experiments/remote-workspaces/README.md) explicitly disclaim real SSH, real provider, daemon installation, process-restart durability and cross-OS transfer. In-memory IDs/dedup there survive client detach only while owner lives. These are placement evidence, not a production remote feature.
- [Earlier research](ssh-research.md) distinguishes remote CLI, remote runtime plus local UI, and local agent plus file/shell proxy. The last cannot preserve ordinary Bun/node fs/import semantics or offline thinking. A remote shell continuing is not a remote agent continuing.

## Primary Codex/OpenAI checks (observed 2026-09-26)

- [Codex app-server](https://developers.openai.com/codex/app-server) documents JSON-RPC over default stdio JSONL, experimental WebSocket, and Unix socket; `codex --remote` can attach a CLI terminal UI to an app-server listener. For nonlocal connections it calls for TLS and WebSocket auth; plain ws is for loopback/SSH forwarding. Its own docs say app-server command and WebSocket transport are experimental and unsupported for production, and non-loopback listeners currently allow unauthenticated connections by default unless explicitly configured (capability-token or signed-bearer flags). Do not expose a listener publicly. `--code-mode-host` is an **outbound Code Mode host**, not an inbound remote attachment or durability switch.
- Same protocol has `initialize` per transport connection, `thread/resume`, `thread/read`, `thread/list`, `thread/loaded/list`, `turn/start`, `turn/completed` and server-to-client approvals/elicitation. `thread/unsubscribe` docs explicitly say that with no remaining subscribers the server unloads the thread after an inactivity grace period. **Neither WebSocket transport nor resumable stored thread history proves that a running turn continues after the last client disconnects or the server dies.** Documentation does not promise offline agent-loop survival here; a test of actual disconnect and approval behavior is required before borrowing this pattern.
- [Remote connections](https://developers.openai.com/codex/remote-connections) says the desktop app uses SSH to start/manage a *remote Codex app server* through remote login shell; install and authenticate Codex on host and have `codex` on PATH. Remote project reads, writes and commands happen remotely. But its phone Remote feature connects to an awake/online desktop host: if that host sleeps, loses network or closes app, remote access stops. Its SSH project setup is not a promise that a laptop-offline controller keeps thinking. Host-to-host chat handoff interrupts an in-flight response and transfers chat/Git state; it is not live-turn continuity. Docs advise VPN/mesh rather than directly exposing app-server on shared/public network.
- [Codex authentication](https://developers.openai.com/codex/auth) supports ChatGPT or API key for local CLI/IDE; Codex cloud requires ChatGPT. It describes credentials stored in `~/.codex/auth.json` or OS credential store, refreshed during active ChatGPT sessions, and device-code authentication for remote/headless CLI. These are Codex-specific, **not** die's credential file format or license to copy tokens. [Codex cloud](https://developers.openai.com/codex/cloud) offers hosted isolated tasks, not arbitrary user-owned SSH Linux environment with user's CLI and secrets by default.
- Attempted `tvly search` for app-server/auth and `tvly extract` for the app-server page; search returned primary page snippets, extract reported “Error fetching content,” then keyless tvly hourly cap was reached. Cross-checked the cited primary HTML pages directly with curl. No claim about internal Codex disconnection policy beyond the published behavior above.

## Simplest architecture matching this requirement

**First ship remote-installed die as the authoritative agent, with SSH terminal attach (or a remote PTY in a durable multiplexer) and no local controller in the critical path.** Install a compatible Linux die+Bun/runtime on the server; remote process owns model calls, cwd, execute, jobs/subagents, skills, questions, session history, secrets and output. SSH config/host-key verification stays on laptop. Run agent under an explicit, user-owned long-lived server supervisor or tmux-like session so SSH hangup is **detach**, not SIGTERM; attach/reconnect using server session identity and read authoritative history/status without resending the prompt. Make client detach distinct from user stop, and ensure approvals/questions have a remote persisted inbox or explicit blocked state rather than silently granting/losing them. Server must have outbound model access and locally provisioned credentials to work during laptop outage. This sacrifices integrated local TUI/Live initially, but makes offline continuation testable without inventing a distributed tool protocol.

If the product needs native local UI, add a **thin attach client** to that same persistent remote agent owner, over SSH forwarding/stdio and authenticated private socket, rather than moving model loop back to laptop. Explicit service lifecycle, session/turn/job IDs, bounded persisted events, acceptance vs delivery ACK, status reconciliation after ambiguous link loss and server restart behavior are necessary; do not blindly replay mutating requests. Choose and document durability scope: disconnect (running server) versus reboot/crash (needs persisted state and rehydration; an in-flight model turn may be unknown). Do not claim tmux by itself provides crash recovery. Local laptop-only tools can be optional online-only capabilities with visible blocked state.

Provisioning should be narrow and explicit: remote provider sign-in/device flow or scoped API key saved under remote permissions; selected plain-text skills/config synchronized with consent; Linux-native CLI installation and separate remote CLI credentials (e.g. gh/cloud), not Mac binaries, host keychain export or SSH agent-forwarding as a model-auth dependency. Show exact paths, ownership and network/secret requirements. Validate on real SSH Linux by dropping laptop network *and* killing client, then see subsequent autonomous model turn/tool use, pending approval behavior, child tasks, and reconnect without duplicate side effects; separately test runtime kill/restart and lack of provider connectivity. Current experiments do not establish any of those.
