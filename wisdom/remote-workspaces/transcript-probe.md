All four original representations decode to the same 18 JSON values in order, including agent_end's repeated messages, tool outputs, usage and event envelopes. Raw includes one newline per event; arrays have no newline. No status summary-only shortcut, no dedup/projection. Original encode/decode median ms per transcript: raw JSONL 0.059 / 0.299; per-event gzip 0.471 / 0.203; batch+gzip 0.564 / 0.157. Decode paths differ (raw decoder includes chunked bounded JSONL parsing; compressed decode gets complete frames), so differences are *not* a pure codec speedup. Frames batch at 4 KiB or 40 ms from first event; single oversized events emit alone. Largest observed intra-batch event-time spread 28 ms; timer is **modeled**, not running in this offline probe. First event 289 raw bytes, 192 per-event gzip bytes; it is alone in a 290-byte JSON array or 192-byte gzipped array and would wait up to 40 ms if a timer rather than byte cap flushes it. Never infer network first paint from this.

Simulated independent copies of the *original* fixture (no additional processes): 100 streams = 3,424,200 raw / 1,441,500 per-stream event gzip / 1,259,400 per-stream batch gzip bytes; 1000 = 34,242,000 / 14,415,000 / 12,594,000. By contrast, compressing all identical streams as one continuous gzip yields 253,415 bytes at 100 and 2,574,827 at 1000; this is **shared-dictionary optimism**, not independent-stream traffic (and even independent streams share identical source text here). Real distinct histories are likely less compressible. All numbers exclude record envelope outside JSON event, gzip transport flags beyond gzip payload itself, HTTP/SSH/TCP framing, requests, acknowledgments, status sync, disk cost, link latency, server UI and authenticated RPC effects. The simplest default remains append-only raw JSONL, optionally bounded gzip batches if real measured bandwidth justifies added latency/CPU; per-event gzip trades bandwidth for compressor calls, without batch wait. Keep payload content intact for offline transcript replication.

Arbitrary byte chunks: splitting between UTF-8 bytes of `café 🔥 中文`, `fin 😄`, newline and every other boundary, plus one-byte feeds, reconstructs exactly. Recreating a TextDecoder **per chunk** inside the emoji inserts U+FFFD (observed); split on raw LF bytes, buffer incomplete record bytes, then fatal-decode a complete line (or use one persistent streaming TextDecoder with fatal final flush). On EOF with trailing bytes report **incomplete**, not a partial silently accepted record; invalid UTF-8 and malformed JSON fail. The stand-alone decoder caps pending and complete records at 65,536 bytes by default, tests an 8-byte cap; this deliberately rejects rather than truncates oversized output. A production protocol needs explicit upper byte/time bounds for a missing newline and idle partial frame, plus size policy for genuinely larger tool outputs (chunk/attachment with integrity or explicit rejection). Time cap here bounds batching only, not decoder lifetime. On reconnect require owner identity/epoch and contiguous sequence/cursor verification, reject gaps, resume/refetch from retained owner where available; cannot infer absent records or repair a lost owner. The fixture parser tests contiguous sequence from 1 but is not a full reconnect implementation. None of this proves durability, SSH behavior, real user questions, Mac transport, or exactly-once tool effects.
