# Remote SSH tasks vs existing jobs — architecture audit (recommendation, NOT implemented)

Read alongside `src/remote/README.md` and `wisdom/values.md`. The smallest correct integration is **one session-owned job projection and one parent delivery path**, not another remote completion inbox. Existing remote SSH ownership, journal and recovery stay authoritative; do not pretend an SSH owner is a local child process or a T3-scoped native task.

## Actual call paths today

- `src/agent/extension.ts` registers `createRemoteOperations()` at execute method `remote` (around 530–541); `src/remote/operations.ts` routes launch/launchRepository/sync/transcript/cancel to `RemoteClient`. Human `/remote` in `src/remote/extension.ts` creates a **separate** client, polls `syncActive()` every 5s and on session start, and calls `pi.sendMessage({customType:"die-remote", display:true})` on changed fingerprints. This prints a message; unlike the job completion batcher it does not trigger a parent turn. `seen` is process-local and all cached tasks can be announced again on restart; terminal payload can include the last assistant message. The execute launch returns a cached summary, not a background job registration.
- `src/remote/client.ts` persists `~/.die/remote/state.json`: host, SSH ownerId/epoch, taskId, pinned intent, transcript cursor/events, terminal observation, cancellation intent, artifacts and errors. Launch persists intent before SSH and retries same ID only; `syncRaw` validates contiguous seq/cursor and checkpoints pages; `syncActive` round-robins outstanding/unfinished tasks. `src/remote/owner.ts` persists task state/journal and runs the child session, refusing uncertain duplicate launches; cancellation is request/report + observed settlement, not instant success. Repository return and capabilities are serviced on `client.sync` (`src/remote/services.ts`); no projected terminal status should bypass that servicing.
- `src/agent/extension.ts` owns session-local `TaskManager`, `JobAttentionScheduler`, `CompletionBatcher` and print/json `agent_end` boundary (roughly 244–320, 373, 611–690). Manager completed events wake the boundary; attention notices wake it; the batcher delivers via main owner `sendContext` or `pi.sendMessage(..., {deliverAs:"steer", triggerTurn:true})`. `src/tasks/job-service.ts` routes local jobs to manager; in T3 environment lists native scoped tasks through adapter, observes and cancels by ID, stopWork discovers all native pages before cancellation. Native terminal delivery is deliberately T3-owned, not sent through local batcher. Local shell/CLI tasks support input/snooze/watch and callbacks; scoped native tasks only list/inspect/stop. `JobAttentionScheduler` subscribes to manager events, not remote cache.

## Recommended smallest slice

1. Establish **parent-session ownership when launching**, in durable remote cache (session ID/branch or session file identity, plus source/client identity as needed). Existing SSH ownerId/epoch identifies the *server*, not the parent session. Historically unowned cache entries stay available to human `/remote` but must not awaken an arbitrary parent. Reopen/reconnect the matching parent only; branch/session switches cannot inherit other sessions' work. Ensure human command launches and execute launches use the same ownership rule. Explicitly define whether human launches without an active agent session are human-only.
2. Build a narrow remote job adapter/projection into the existing session job service: list cached owned SSH tasks alongside local and T3-native (stable pagination; offline cache marked stale), inspect from cached transcript/status with bounded offsets and explicit gap/truncation semantics, stop by `RemoteClient.cancel` with requested/pending/unknown vs confirmed terminal distinguished. Extend stopWork discovery to owned remote tasks and report partial offline discovery/errors honestly. Do **not** route unknown IDs blindly to T3 adapter: local IDs, T3 IDs, SSH IDs need explicit disjoint namespacing (e.g. public `ssh:<opaque taskId>`) and reversible validation; preserve raw SSH taskId for SSH wire, and migrate/resolve existing unprefixed IDs deliberately. Cursor format/version must account for the third source, and not expose a global remote cache as session jobs.
3. On remote cache observation transitions, feed only **new terminal transitions for owned tasks** into the existing completion batch and print/json boundary (or a small shared job event interface consumed there); feed running/quiet attention to the same scheduler policy if supported. Reuse batching, parent wake, main-owner delivery, dedup of completion vs attention, and session teardown semantics; avoid sending full assistant terminal output again through independent `die-remote` notifications. Human remote UI can retain concise question/capability/actionable notices, but completion should have one owner. UI changes are a separate concurrent task.
4. Persist a delivery watermark/terminal fingerprint per (parent session, SSH ownerId/epoch, taskId), separate from transcript cursor and `extension.ts` ephemeral `seen`; atomically establish claim before turn delivery or use existing durable local delivery/outbox semantics. A transient failure must be retried, not marked delivered; terminal repeats, app restart, reconnect, concurrent refreshes and post-terminal artifact updates must not create extra completion turns. If exactly-once acknowledgment is unavailable, document at-least-once with idempotent envelope and bounded retry rather than claiming exactly once. Recheck running state after subscribing, as existing parent boundary does, to close the finish-before-subscription race. Polling is still needed to discover server changes over SSH; it is **not** a second notification system.

## Boundaries / review traps

- `TaskManager` owns actual child processes and in-memory completion promises; SSH tasks survive process exit, may be unreachable and have persistent journal gaps. Do not fabricate local `TaskInspection` process exits, stdin, kill acknowledgment, or status `done` from a cached error. Adapter should expose source/observedAt/staleness and honest unknown states. T3's backend authenticated list is session-scoped and terminal delivery is T3-owned; SSH remote owner is host-level and needs explicit local parent attribution. `jobs.input/closeInput/snooze/setWatch` should reject SSH IDs unless an actual implementation exists; `jobs.stopWork` does not imply remote cancellation is settled.
- Preserve remote launch/reconcile safeguards, pinned owner epoch/intent, transcript cursor checks, cancellation report, question ownership, capability grants and repository return. A remote result arriving as a UI dump is evidence of transport/refresh, **not** evidence of parent resume. Test with execute launch + parent yields, terminal server result + parent wake once, app restart/offline/reconnect, two sessions sharing one remote cache, repeated sync, stopWork offline/partial, and completed job inspect/list after reconnect.

No production implementation in this audit; follow-up should review concurrent coordinator-wake and UI-spam workers against this single-jobs-path recommendation before merging.
