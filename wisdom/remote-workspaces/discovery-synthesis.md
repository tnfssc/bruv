# Remote workspaces: discovery synthesis

The target is one Mac and one Linux host with die already installed and authenticated on Linux. These are mostly isolated Linux/Docker fixtures, not a working Mac-to-Linux product. The [experience contract](task-experience-contract.md) is a checklist, not shipped behavior. Build **one thin end-to-end CLI experience next**, not another round of separate transport/codec probes or fleet machinery.

## What the proofs actually establish

- A real die RPC process on Linux, driven by a fake model, made three model turns and two real execute calls after its client disappeared for four seconds; a later viewer saw its final assistant message. The later durable owner/replica fixture retained full tool/model events for offline reading after the owner stopped. This proves detached execution in the fixture, **not** live provider access or Mac sleep/wake. [Agent](remote-agent-probe.md), [durable task](task-poc.md).
- The Docker SSH fixture pinned the host key, kept task HTTP inside the forward, severed the client forward during a tool, reconnected and read a full cached transcript offline after containers stopped. A separate combined SSH fixture exercised a **native persisted /questions** prompt/reply over packaged RPC with a stable reply ID and duplicate handling, but its offline artifact was a bounded readable status snapshot, **not** a full transcript. The ownership bug found by the first native probe (diagnostic sibling ahead of toolResult) was fixed and retested; this is fake-provider Linux loopback, not human approval or hardened same-account isolation. [SSH transport](ssh-transport-probe.md), [combined questions](ssh-native-question-combined.md), [ownership fix](native-question-ownership-fix.md).
- A real accepted launch reply was dropped after the owner accepted it: the client got ECONNRESET, and retrying the same ID/spec found exactly one acceptance. SIGKILL during execute left an **unknown** outcome across owner epoch 1→2, not a failed or automatically resumed task; a completed but unrecorded side effect cannot be safely replayed. Replica partial lines were rejected. This is narrow process/socket-fault evidence, not power-loss durability or exactly-once effects. [Failure probe](failure-probe.md).
- A disposable Git-only repo handoff transferred selected tracked changes, omitted untracked/ignored contents, and refused stale return on changed HEAD, tracked diff or index entries without changing fixture bytes. No atomic capture/apply, secret-filtered history, real repo transport or Mac workspace integration is proven. [Repo probe](current-repo-probe.md).

## UX and wire observations (scoped)

- Cached history must open **before** network contact. Show last sync time/cursor and offline/unknown freshness separately from live status: a cached “running” label is not a fresh observation, offline is not failed, and a snapshot is not the full tool/assistant transcript. Persist contiguous events with the cursor; surface gaps, output availability and changed owner epoch. The task fixture has full cached content; the combined SSH question fixture has only a bounded snapshot. [Contract](task-experience-contract.md), [task POC](task-poc.md), [combined questions](ssh-native-question-combined.md).
- Linux Docker SSH parent repeats measured 170 ms cold hello, 45 ms connected launch and 176 ms fresh reconnect plus catchup, single local samples, not WAN latency; its replica held 34,242 bytes of event JSONL for 18 events. Complete-transcript offline codec test: 34,242 raw bytes versus 12,594 gzip-batched bytes (9 frames), preserving all 18 event values; 40 ms batch wait was modeled, not network-tested. [SSH](ssh-transport-probe.md), [transcript](transcript-probe.md).
- Synthetic 10 active / 1000 total tasks: replaying history was 2,563,762 JSON payload bytes, full event deltas 228,879, lazy deltas 49,579 **plus 178,940 output bytes to fetch**. Summary catchup is not offline transcript replication. In the loopback application-delay stream fixture, one task at 300 ms per direction showed about 983 ms question visibility with direct data-bearing long poll versus 1,588 ms with hint-then-fetch; extra RTT matters. Neither test measures WAN packets, SSH backpressure or production CPU. A separate Docker network fixture at 300 ms each way saw median visible done 1,806 ms versus 465 ms baseline for three tiny scripted tasks per condition; no tails. Favor a simple bounded full-event catchup/active stream until real UX warrants compression or lazy output. [Wire](wire-bench.md), [stream](stream-probe.md), [network](network-lab.md).

## Decisions and remaining risks for the first experience

Connect should show host/version and **remote** default provider/model/thinking, never credentials. Configured auth is not verified provider access. Current die profile fallback expects a parent context; the fixed fake-model POC does not prove remote default discovery. Resolve one remote normal default (or fail clearly), record effective config at acceptance, reject unsupported overrides rather than silently using the Mac Live model; repo choice is separate. Save launch ID and intent before sending, distinguish pending/confirming from accepted/running and reconcile ambiguous replies by the same ID. [Profile discovery](remote-profile-discovery.md), [contract](task-experience-contract.md), [failure](failure-probe.md).

Keep a native question visible until genuinely answered/delivered; RPC success alone once masked an ownership rejection. An on-demand local-file capability and denial path were exercised only through scripted typed fixture records: there is no real Mac permission UI or isolation from a same-UID arbitrary agent. First local capability should be one explicitly granted, read-only, bounded invocation with visible destination/arguments and ID; wait when Mac is absent, do not grant remote arbitrary shell. For repo tasks, show base/snapshot, chosen dirty paths and omitted files; return a reviewable artifact, refuse stale local state rather than auto-merge. An SSH key, remote account/provisioning, real authenticated provider and refresh, Mac sleep, cancellation, owner restart reconciliation and disk/power loss remain untested. [Dependency slice](task-poc.md), [questions](ssh-native-question-combined.md), [repo](current-repo-probe.md), [contract](task-experience-contract.md).

**Smallest next integrated user-facing test:** with preinstalled/authenticated die on the one Linux server, use a Mac CLI to inspect the remote default, launch one real remote task (start with a controlled fake profile for repeatability, then verify real-provider auth separately), disconnect/close Mac during its tool turn, reopen cached *full* transcript offline, reconnect through pinned SSH and catch up, answer one real native question, grant or deny one read-only Mac fixture on demand, and inspect a repo result against changed local state. Show pending, stale, waiting, accepted, unknown and done honestly. Keep one owner/task and bounded history; record observed first progress, reconnect/catchup and bytes on this actual path. If a slice is too large, stage the capability and repo return **within the same CLI path**, not as more standalone proofs. Existing [values](../values.md) already cover truthful surfaces, safety and simplest workable design; no values edit.
